# Система модулей Aster Mail — API 1

Платформа API 1 включена в Aster Mail 0.2.0. Провайдеры распространяются
через отдельный [репозиторий модулей](https://github.com/darxfame/aster-mail-modules).
Учебный пакет `examples/modules/sandbox-demo` использует вымышленные данные
и не устанавливается автоматически в пользовательский аккаунт.

## Требования и решение

Модуль — самостоятельный пакет с JavaScript-логикой, собственными HTML/CSS-частями, командами, хранилищем и обменом событиями. Ограничиваться декларативным HTTP-коннектором нельзя: нужны многозапросные сценарии, собственные формы и взаимодействие с приложением.

Для недоверенных пакетов выбран Chromium sandbox, а не `require()` в Electron main, Node.js-процесс или `node:vm`. Код модуля загружается только как браузерный ES module в отдельное скрытое окно. UI размещается в отдельных `WebContentsView`, а не в DOM почты. Node.js и нативные библиотеки недоступны. Браузерные зависимости разработчик собирает внутрь пакета.

Типы пакетов классифицируют назначение, но не выдают права:

| Тип | Назначение |
| --- | --- |
| `integration` | Внешний сервис: видеовстречи, справочники, корпоративные системы |
| `workflow` | Сценарии и команды над разрешёнными API приложения |
| `panel` | Самостоятельная панель/встраиваемая форма |
| `hybrid` | Сочетание перечисленных возможностей |

## Устройство

- `desktop/modules.cjs`: контракт, ограничения пакета, snapshot ресурсов, SHA-256, установка, сетевой посредник.
- `desktop/module-host.cjs`: runtime, привязка к аккаунту, разрешения, RPC, события, встраиваемые представления, остановка.
- `desktop/module-preload.cjs`: узкий мост модуля; не предоставляет `ipcRenderer` или API Aster.
- `desktop/module-runtime.mjs`: запуск `activate(api)` и обработчиков команд в sandbox.
- `src/modules-ui.js`: управление пакетами, кнопки в разрешённых местах, host-часть встраивания, проверка актуального черновика.
- `desktop/main.cjs`: существующий доверенный IPC и адаптер ограниченных возможностей календаря/черновика; операции отправки модулю не выдаются.

Пакет содержит `module.json`, основной ES module и локальные ресурсы. Установка из выбранной папки или публичного GitHub-репозитория создаёт копию в `userData/modules/<id>/<version>-<digest>`. Исходная папка больше не используется. Символьные ссылки, выходы за пределы папки, неподдерживаемые файлы и слишком большие пакеты отклоняются. Манифест явно перечисляет `files`; неописанные файлы не используются. Файлы читаются в ограниченный snapshot; runtime обслуживает только этот snapshot. SHA-256 проверяется перед запуском и при чтении каталога. Подписи издателя и магазин пакетов в API 1 не предусмотрены: fingerprint защищает целостность установленной копии, а не доказывает репутацию автора.

## Жизненный цикл

1. Пользователь подключает аккаунт обычным способом; наличие модулей не должно блокировать вход.
2. В «Настройки → Модули» выбирает папку пакета или публичный GitHub-репозиторий, ref и папку в нём. До согласия код не выполняется.
3. Aster показывает имя, версию, fingerprint, разрешения и HTTPS origins. Пакет устанавливается выключенным.
4. При включении пользователь отдельно разрешает возможности для текущего аккаунта.
5. Кнопки и места для UI берутся из манифеста. Runtime запускается по первой команде или открытию UI. `activate(api)` должен завершиться за 15 секунд.
6. Команда получает входные данные и разрешённый контекст; повтор одного активного вызова блокируется. Ответ ограничен по размеру и времени.
7. Ошибка/тайм-аут/падение прекращает работу экземпляра. Автоматического повтора запросов и команд нет. Пользователь может заново запустить модуль явным действием.
8. Отключение, смена аккаунта и выход закрывают runtime и UI, отменяют сетевые запросы, отклоняют ожидающие команды и удаляют память сессии. Старый ответ не должен попасть в другой аккаунт или черновик.

Состояние и секреты модуля сохраняются через существующий зашифрованный LocalStore в отдельной записи модуля. Код пакета хранится отдельно от данных аккаунта. Метаданные и настройки аккаунта подчиняются существующим правилам удаления Aster при выходе/переключении аккаунта; установленная копия кода может оставаться на диске. Секреты не попадают в каталог модулей, манифест, логи или renderer основного приложения.

## Граница безопасности

Runtime и UI используют `sandbox: true`, `contextIsolation: true`, `nodeIntegration: false`, `webSecurity: true`, отдельную непостоянную session и собственный preload. При `--no-sandbox` запуск запрещён.

Ресурсы доступны только из внутреннего HTTPS origin текущей session. CSP запрещает inline-скрипты, `eval`, внешнюю сеть, iframe, формы, объекты и workers/service workers. Отдельные части интерфейса создаёт host. Новые окна, навигация, скачивания и запросы разрешений запрещены. Файловые URL не обслуживаются. Direct requests дополнительно блокируются `webRequest`; session использует принадлежащий Aster loopback proxy, который отклоняет все запросы и CONNECT, а WebRTC — `disable_non_proxied_udp`. Сетевой SDK работает через ДРУГУЮ session, без cookies и учётных данных Exchange.

RPC принимает сообщения только от зарегистрированного runtime/UI и его главного frame. Сообщения ограничены до отправки из preload и после приёма в main. Для каждого метода проверяются заявленное разрешение, актуальность аккаунта и контекст действия. Количество параллельных запросов и частота ограничены. Сообщения со старыми nonce/из чужого frame игнорируются.

Это не обещание отсутствия уязвимостей Chromium: Electron необходимо обновлять, а перед производственным внедрением нужны отдельная проверка границ песочницы и платформенная приёмка Windows/macOS. Права `calendar.read` + `network` позволяют модулю передавать доступные календарные данные объявленным сервисам — пользователь должен понимать это при выдаче разрешений.

## UI и внутренние взаимодействия

Команды добавляются в меню модулей в верхней панели, в панели календаря или рядом с полями создания встречи. Поддержан также `internal` — команда только для собственных UI и других команд пакета, без кнопки в Aster.

Представления типа `panel` открываются как собственная панель внутри диалога Aster; `meeting.create` встраивается в новую встречу. Размеры, clipping, масштаб, позицию и жизненный цикл определяет host. Произвольное изменение DOM приложения, CSS почты и перехват основных кнопок запрещены. При открытии другой формы/закрытии диалога native-представления удаляются. Позднее завершение создания UI отбрасывается по revision.

Модуль получает собственные события и события других включённых модулей только с правом `events`. Тема собственного события принудительно получает префикс `<module-id>.`; подделать `calendar.changed` нельзя. Core публикует `calendar.changed` после успешной пользовательской операции с календарём без содержимого встречи. Произвольного перехвата RPC, сетевых запросов Exchange или жизненного цикла отправки нет.

## Лимиты API 1

- До 8 подключённых модулей на аккаунт; до 200 файлов и 10 МиБ на пакет; до 16 КБ на манифест.
- До 12 команд и 12 представлений в пакете, до 4 одновременно встроенных представлений.
- До 8 HTTPS origins; сетевые вызовы — JSON, до 64 КиБ, 30 секунд, без redirect/retry.
- RPC — до 64 КиБ, до 32 параллельных запросов и 40 обращений/секунду на экземпляр; команда — до 30 секунд.
- Хранилище пакета — JSON до 16 КБ, только зашифрованное хранилище host.
- Чтение календаря — основной календарь, интервал до 31 дня, максимум 200 записей. Результат не является подтверждением отсутствия конфликтов.
- Контекст черновика — только открытая НОВАЯ встреча, без адресов участников; описание до 8000 символов с признаком усечения. `start/end` — UTC или `null` при незавершённом вводе. Фоновая отправка приглашений не поддерживается.

## Интеграции провайдеров

SDK предоставляет общие механизмы входа, запуска desktop-приложения и обновления
настроек. Конкретные сервисы, их origins, формат сессии и реализация находятся
в отдельном репозитории модулей. Совместимость проверяется по manifest и возможностям
SDK. Создание комнаты и отправка приглашения остаются разными действиями:
модуль предлагает ссылку в черновик, отправку выполняет пользователь.

Основания исследования:

- [Electron: Security](https://www.electronjs.org/docs/latest/tutorial/security/).
- [Electron: Process Sandboxing](https://www.electronjs.org/docs/latest/tutorial/sandbox).

- [Контур.Толк: персональный API-ключ](https://support.kontur.ru/talk/86797-personalnyj_apiklyuch_dostupa_v_tolke).

## GitHub и рассмотренные образцы Xerj

Реализован `desktop/module-github.cjs`: canonical GitHub repo URL + ref + directory → точный commit SHA → module.json → объявленные файлы → общий snapshot/digest → пользовательское подтверждение → установка выключенного пакета. API и raw-file загрузки используют отдельную session без credentials/cookies Exchange. Источник привязывается к commit; Git и scripts репозитория не выполняются.

По прямому запросу пользователя изучены образцы [Xerj pack verification](https://github.com/xerj-org/xerj/blob/v1.0.0-rc.100/engine/crates/xerj-hub/src/pack.rs), [Xerj lockfile](https://github.com/xerj-org/xerj/blob/v1.0.0-rc.100/engine/crates/xerj-hub/src/lockfile.rs) и [agent plugin](https://github.com/xerj-org/xerj/blob/v1.0.0-rc.100/plugins/xerj/README.md). Полезны принципы фиксирования источника, проверки целостности и ограничения пакета. Код не копировался. У Xerj Corpus Hub есть отдельная проверка подписи; Aster API 1 НЕ заявляет аналогичной подписи издателя.

Xerj подключается только как необязательный инструмент разработки. Его использование не является условием разработки модулей или сборки Aster; каждое применение требует отдельного согласия пользователя.

## Каталог и обобщённые возможности SDK

В `codex/module-catalog` добавлены чтение авторского `catalog.json`, список карточек
и установка/включение одобренной версии одним нажатием. До установки проверяются
актуальная ревизия каталога, commit пакета, manifest и digest. Отсутствующий файл
каталога показывается как «ещё не опубликован», а сетевой сбой — как ошибка со
возможностью обновить список. Опубликованный формат и точные версии пакетов проверяются по каталогу основной ветки репозитория модулей.

`auth.session` и `meeting.launch` — общие capabilities с декларативными параметрами
в manifest. Код конкретного сервиса и его ресурсы в репозиторий Aster не входят.
Окно входа использует отдельную session; токены не возвращаются общему renderer.
Маршрут встречи применяется только по пользовательскому действию и с проверкой
системного обработчика. Полный контракт и ограничения — в руководстве разработки.

Проверено: реальная карточка в Electron, одно нажатие → «Уже подключён», установка
включённого пакета без лишних запросов, стандартная песочница, декларативное
получение вымышленного токена в реальном sandbox-окне, logout и retirement,
системный protocol lookup, прежний вход OWA и первое чтение. Пакетные сборки не
запускались. Windows и реальные провайдеры требуют отдельной приёмки.

Итог Node-проверок этого дополнения: 334 успешно, одна пропущена; `npm run check`, `test:module-sdk`, `test:modules -- --catalog-live` и `test:connection` прошли.

## Проверка публичного каталога и совместимого пакета

Исправлен просмотр до входа и в desktop demo: публичный IPC использует отдельную
непостоянную session и не читает аккаунт. Установка по-прежнему account-scoped.
Добавлены поддержка опубликованного индекса schemaVersion 1 и общие optionalOrigins
с нативным подтверждением точного HTTPS origin. Ошибки code/status создаются
обёрткой в мире модуля, чтобы Electron contextBridge не терял их поля.

Node: 338 успешных проверок, одна пропущена. Нативные SDK, песочница и обычное
подключение прошли. Из настоящего каталога GitHub установлен и включён ktalk 0.1.1
в вымышленном аккаунте; manifest, capabilities и SHA-256 совпали. Внешний пакет
опубликован в aster-mail-modules с тегом v0.1.3; реализация сервиса в Aster не входит.
Проверки пакета в его репозитории: 11 Node и реальный Electron со служебными
вымышленными ответами, включая grant, 404, шифрованное состояние и единственный PUT.
Реальный корпоративный SSO и Windows этим не подтверждаются.
